# Architecture decisions — UsageMap's design-decision log

This log states every design decision of UsageMap in one place, precisely enough to build from. Each ADR entry has a
full document (`NNNN-title.md`: Context / Options considered / Decision / Consequences / Research basis). If an ADR
and this log disagree, fix both in the same change. Spikes `S-xx` named below are the throwaway experiments in
[`spikes/`](../../spikes/README.md), each with a README stating what it proved. Capability IDs (`area.name`) refer to
[`docs/capabilities.md`](../capabilities.md).

**Status of all entries: Accepted.** Decisions that rest on an unexecuted spike say so.

**Read the decision tables at the end (C-01 … C-180) together with the ADR summaries.** They were written as the
design and the build exposed gaps; where a numbered decision and an ADR summary differ, the numbered decision wins,
and a later number wins over an earlier one.

## System at a glance

| Component | Path | Language | Role |
|---|---|---|---|
| tracker | `/tracker` | TypeScript → single classic script + ESM npm package | Browser instrumentation; pinned, zero runtime dependencies |
| gateway | `/services/gateway` | Go | The only public entry on edge nodes: TLS, tracker files, challenge, web collect, OTLP front door (token auth, rate limit), verdicts, spool, forwarder |
| collector | `/collector` | Go (custom Collector distribution built with `ocb`) | Loopback-only OTLP pipeline: sanitise + normalise, spans → metrics, persistent queue, export to writer |

| metrics-writer | `/services/metrics-writer` | Go | OTLP/HTTP in → de-duplicate → cumulative-to-delta → additive upserts into PostgreSQL |
| engine | `/vendor/umami` | upstream Umami, unmodified | Web analytics engine (sessions, visits, metrics); private network only |
| control-plane | `/services/control-plane` | TypeScript (Node, Fastify) | REST API (OpenAPI 3.1): auth, tenants, sites, services, enrollment, keys, audit, erasure, tenant + operator metrics APIs |
| jobs | `/services/jobs` | TypeScript | Scheduled workers: partitions, retention, web rollups, trust scoring, registry sync, domain verification, on-chain correlation, snapshots |
| portal | `/apps/portal` | TypeScript (Vite + React SPA) | Tenant and operator UI, onboarding wizard |
| engine proxy | `/services/engine-proxy` | Go | Internal front of Umami on core nodes: per-node mutual TLS, path allow-lists, visit-token memory (C-60, C-74) |
| health controller | `/services/health-controller` | Go | Probes edge and core nodes and maintains the DNS record sets at both providers (C-92) |
| on-chain reader | `/services/onchain-reader` | Go | Optional reader of public ledger files (C-42) |
| infra | `/infra` | OpenTofu, Ansible, Docker Compose | Everything needed to rebuild |

Databases: one PostgreSQL 18 cluster with two databases — `scf` (ours, RLS everywhere) and `umami` (engine-owned).
Placeholders used in the design documents: domains `<domain-a>`, `<domain-b>`; repo `ORG/REPO`; npm `@SCOPE/tracker`.

## Register

### ADR-0001 — Licence
Our code, IaC and docs are **Apache-2.0** (SPDX headers, `LICENSE`, `NOTICE`). Umami (MIT) is consumed unmodified.
Dependencies must be on the allow-list of OSI-approved licences (MIT, BSD-2/3, ISC, Apache-2.0, MPL-2.0,
PostgreSQL, Unlicense, 0BSD, Zlib; GPL/AGPL/LGPL only for separately run, unmodified tools such as Ansible, Grafana,
HAProxy — never linked into our code). Excluded: BSL, TSL, SSPL, ELv2, "open-core" `ee/` code. Data sets are not
code: DB-IP Lite (CC BY 4.0) and iptoasn (PDDL) are used with attribution and recorded in `NOTICE` (design trade-off DV-03).

### ADR-0002 — Base project: Umami
**Umami v3.5.0** (commit `d3c62a8`). Weighted scorecard 363 vs 186 of 500 for GoatCounter. Decisive: Umami computes all seven required web metrics natively;
GoatCounter lacks bounce rate, session duration, raw pageviews and de-duplicated uniques, has one maintainer and a
modified EUPL. v3.5.0 is the minimum safe version (earlier releases carry known vulnerabilities).

### ADR-0003 — Integration strategy: wrap an unmodified private engine
- Umami runs **unmodified** and is **never reachable from the internet**. We build the image ourselves from the
  pinned commit (fetched by SHA, checksum-verified) with `SKIP_BUILD_GEO=1`; `vendor/umami/patches/` is an empty
  patch queue kept so a fix can ship within 24 h when upstream has none.
- Write side: only the gateway's forwarder calls `POST /api/send`.
- Read side: the control plane calls Umami's stats API through one adapter package (`packages/umami-adapter`),
  authenticating as a **per-tenant view-only Umami user** (one Umami team + one view-only user + one API key per
  tenant, provisioned by the control plane with an admin identity used for provisioning only). A mapping bug in our
  code therefore still cannot cross tenants inside Umami.
- Direct SQL against the `umami` database is limited to two jobs — retention and erasure — through a narrow role.
- Hardening: `DISABLE_TELEMETRY`, `DISABLE_UPDATES`, `PRIVATE_MODE`, `SALT_ROTATION=day`, `TZ=UTC`,
  `CLIENT_IP_HEADER=x-scf-surrogate-ip`; default admin password replaced at bootstrap; no egress from the engine
  network; MCP off; shares never created.
- Upgrades: contract tests run the adapter against the real pinned container on every change and nightly against
  upstream's newest tag.

### ADR-0004 — Tracker: our own, pinned
- A **single classic script** with zero runtime dependencies, no `eval`, no dynamic import, no remote configuration,
  no cookies, no web storage (one exception: the opt-out flag), no access to wallet objects.
- **Two pinned profiles per version**: `standard` (built to the French/Spanish/Italian audience-measurement criteria:
  referrer host only, screen-width class, primary language subtag) and `strict` (nothing read through JS APIs beyond
  the page path; no referrer).
- Delivery: immutable URLs `/lib/<semver>/<profile>.js` with `Cache-Control: immutable` and an SRI hash; **no
  `latest` alias exists**; unknown versions return 404. Also an npm package (`@SCOPE/tracker`, ESM) for bundling into
  the tenant's app, which removes the third-party script entirely.
- Tenants upgrade by changing version + hash (or bumping the dependency). Every released version stays served for
  the life of the service unless withdrawn for a security defect (then `410 Gone` — C-37); the wire protocol is
  versioned (`v1`) and backward compatible.
- Behaviour: pageviews (History API aware, hydration-safe), custom events `track(name, props)` with a client-side
  guard that refuses values shaped like e-mails, StrKeys or JWTs, `optOut()` / `optIn()`, GPC and DNT honoured (no
  events sent). Sends with `fetch(keepalive)` + 3 s timeout + bounded retries across a **fixed list of two ingest
  hosts on two domains**; `fetch(keepalive)` on page hide, never `sendBeacon` (C-116).
- Size budget enforced by the tracker's tests: `strict` ≤ 2.5 kB gzip, `standard` ≤ 3.5 kB gzip, both including the challenge solver (C-32).
- Names of the script path, ingest path and hosts are chosen to pass a check against EasyList,
  EasyPrivacy, uBlock Origin, AdGuard and Brave lists.

### ADR-0005 — Web ingest gateway
One Go binary per edge node. Public routes (final names subject to the filter-list check): `GET /lib/…` (tracker
files and signed manifest, compiled into the binary), `POST /v1/c` (challenge), `POST /v1/e` (events),
`GET /healthz`. Per event, in memory:
1. Parse a strict `v1` schema; reject unknown fields; cap sizes.
2. Resolve the site from the public site key; check `Origin`/`Referer` host against the site's verified domains;
   check `Sec-Fetch-*` and client-hint/User-Agent consistency; compute JA4 from the TLS ClientHello.
3. Verify the challenge token and proof (ADR-0008); run the User-Agent bot list; update multiplicity counters.
4. Derive the surrogate address from the full IP and raw User-Agent (ADR-0007, C-34); truncate the IP, resolve
   country and ASN class (ADR-0006), **discard the IP**; reduce the User-Agent to family + major version + OS +
   device class, **discard the raw string**.
5. Assign verdict `verified` / `suspect` / `rejected` with reason codes.
6. Append the rebuilt, allow-listed record to the fsync'd spool and answer `202`. `rejected` events are not
   spooled; only per-site, per-reason counters are kept.
The forwarder drains the spool to Umami `POST /api/send` with `x-scf-surrogate-ip`, `cf-ipcountry`, a synthetic
reduced User-Agent, `timestamp` = time of receipt, and `tag` = verdict. Client-supplied `ip`, `userAgent`,
`timestamp`, `id`, `hostname` never pass through. Site registry, token hashes and limits come from a signed
snapshot pulled from the control plane every 30 s and kept on disk, so ingest continues when the core is down.
The gateway terminates TLS itself (ACME DNS-01 via an embedded library, one certificate per node that includes the
node's own hostname).

### ADR-0006 — IP handling and geo source
The full IP exists only in gateway memory for the duration of one request. Country is resolved from the truncated
address (IPv4 /24, IPv6 /48) using **DB-IP Lite Country** (CC BY 4.0), with sapics `user-country` (PDDL) as
fallback; ASN class (eyeball / mobile / datacenter / privacy relay) from iptoasn + published cloud and Apple Private
Relay ranges. The geo database is fetched at image build by pinned checksum and refreshed monthly by an automated
PR; third-party range lists are handled per C-38. Nothing finer than country is stored. No IP is written to any log, spool, queue or database.

### ADR-0007 — Visitor identifier and salt policy
`surrogate = 2001:db8::/32 address built from 96 bits of HMAC-SHA-256(K_day, site_id ‖ ip ‖ user_agent)`.
`K_day` is random, generated daily at 00:00 UTC, **held only in gateway memory**, shared between gateway nodes over
mutually authenticated private links, never written to disk or to the database, and destroyed at rotation. Umami
then hashes the surrogate again with its own daily salt. Consequences: unique visitors are per site per UTC day;
no cross-site or cross-day identity exists; after rotation nobody — including us — can recompute an identifier. If
every gateway node restarts at once the key is regenerated and that day's uniques are over-counted (documented).
Multi-day "unique visitors" are sums of daily uniques and are labelled so.

### ADR-0008 — Bot and anti-inflation model
Threat: the tenant inflating its own numbers. Eight layers, each with a stated limit:
L0 payload rebuild and field stripping · L1 origin/domain binding · L2 **signed JS-execution challenge** (stateless
HMAC token bound to site, coarse time window, subnet and UA digest; one per page load) · L3 **proof-of-work as
metering** (ALTCHA-v2-style, own ~1 kB solver, adaptive difficulty) · L4 request-consistency signals (`Sec-Fetch-*`,
client hints, JA4, minimal client booleans: `webdriver`, visibility, user activation) · L5 User-Agent bot list at
the gateway **and** Umami's own check left enabled · L6 in-memory multiplicity (distinct surrogates per truncated
subnet per site per window, thresholds by ASN class; Private Relay and carrier NAT carved out; per node) · L7 daily
anomaly detection and an **advisory trust score** with reason codes, computed from aggregates.
Verdicts: `verified` (valid proof, consistent signals), `suspect` (datacenter ASN, multiplicity over threshold,
inconsistent signals, missing proof), `rejected` (no valid challenge, origin mismatch, known bot, malformed). The
verdict is stored as Umami's event `tag`; dashboards show verified and raw side by side. We state plainly that a
real headless browser on residential proxies passes L0–L5 and is only *detectable* by L6–L7. All thresholds are
published. Detection runs per tenant on that tenant's own traffic, in memory (counsel question logged).
*Depends on S-01 (tag filter) and S-07 (PoW timing).*

### ADR-0009 — OpenTelemetry pipeline topology
`tenant SDK or Collector → gateway (TLS, ingest-token auth, per-tenant rate limit, 429/503 + Retry-After) →
loopback → scf-otelcol → metrics-writer → PostgreSQL`.
- Accepted: OTLP/HTTP (protobuf and JSON) and OTLP/gRPC, metrics and traces. **No logs pipeline** — `/v1/logs`
  answers 404 / `UNIMPLEMENTED`.
- `scf-otelcol` is a minimal `ocb` build: `otlp` receiver (loopback, `include_metadata`), `memory_limiter`, our
  `scfsanitize` processor, `filter` (local-root SERVER spans only), `signal_to_metrics` connector (spans → request
  duration as exponential histograms, delta), `otlp_http` exporter with `file_storage` persistent queue
  (`fsync: true`).
- `scfsanitize` runs first and (a) sets `scf.tenant.id` from the gateway-supplied metadata, overwriting anything in
  the payload; (b) keeps only an allow-list of resource and data-point attributes; (c) strips exemplars, span
  events and links; (d) **normalises paths** (ADR-0012) — so nothing unsanitised reaches the on-disk queue.
- Server metrics only (`http.server.request.duration`, legacy `http.server.duration` converted ms → s). Client
  metrics are dropped. Spans are discarded after metric derivation; nothing from a span is persisted.
- Both sources are stored with a `source` label (`sdk_metric`, `span_derived`); reads prefer `sdk_metric` per
  service and day when present, so nothing is double counted and nothing is lost.
- Time bounds: points more than 5 min in the future are rejected; up to 48 h late accepted; no backfill before
  the service was registered.
*`signal_to_metrics` is alpha: version pinned, covered by canary tests; a ~200-line in-house connector is the
fallback. Depends on S-04.*

### ADR-0010 — PostgreSQL metrics schema and histogram representation
Plain PostgreSQL 18, no extensions beyond `pg_stat_statements`. Tables `api_metrics_1m`, `api_metrics_1h`,
`api_metrics_1d`, range-partitioned by time, keyed by `(tenant_id, service_id, route_id, method, status_code,
source, bucket_start)` with `request_count`, `duration_sum`, `duration_min`, `duration_max`, `hist_kind`, `hist`.
Routes live in a dictionary table with the rule-set version. Two histogram kinds, both fixed-length `bigint[]` so
merging is element-wise addition: `explicit15` (the OpenTelemetry default boundaries; exact merge of old-ms and
new-s defaults; percentile accuracy limited to bucket width) and `exp3` (base-2 exponential at scale 3 over
61 µs … 1024 s; relative error ≤ 4.33 %). Tenant exponential histograms are down-scaled to scale 3; span-derived
metrics are produced as `exp3`; mixed aggregates are computed in `explicit15`. Every percentile shown carries its
accuracy class. The writer de-duplicates batches with a ledger table, converts cumulative streams to deltas using
per-stream state in PostgreSQL (reset-aware), and applies additive upserts to all three resolutions in one
transaction. *Depends on S-05.*

### ADR-0011 — Retention and rollups
API: 1-minute rows 35 days; 1-hour rows 25 months; **1-day rows indefinitely** (design minimum 24 months). Web:
event-level data in Umami **90 days** by default (settable 30–395 days — see C-54); daily per-site aggregates (totals plus
top-N breakdowns by referrer host, country, device, browser, OS, path, event name; verified and raw) in `scf`
**indefinitely**. Gateway spool entries are deleted on acknowledgement and never kept longer than 72 h. Rejected-event
counters 25 months. Audit log: life of the service. Retention is enforced by dropping partitions (API) and by a
scheduled delete job (Umami tables).

### ADR-0012 — Path normalisation rules and versioning
A deterministic, ordered, idempotent rule set compiled into `pathnorm` (Go), versioned `scf-path-rules/x.y.z`,
with the version stored on every route. Input precedence: tenant `http.route` (framework placeholders
canonicalised) → span `url.path` / `http.target`. Always: strip query and fragment, collapse slashes, remove
trailing slash, cap depth and length. A closed set of typed placeholders, enumerated in ADR-0012: the vocabulary of the vector corpus (for example
`{account}` for G and M, `{contract}` for C and W, `{signer}`, `{hash}`, `{uuid}`, `{int}`, `{redacted}`) plus
`{overflow}` and `{unknown}`, which the writer assigns (C-16). All ten SEP-23 StrKey types are recognised by shape; the checksum only chooses between a typed
placeholder and `{id}`. Secret seeds, JWTs, API-key-shaped strings and e-mail addresses become `{redacted}` and
increment a per-tenant counter that records neither the value nor a hash. A cardinality guard at write time
(default 1,000 routes per tenant per day, 200 siblings per prefix) sends the excess to `{overflow}`. Optional
closed-set `rpc.method` dimension for JSON-RPC services. The 451-vector corpus is the conformance suite. No
tenant-defined rules. Rule changes create a new version; history is never rewritten.

### ADR-0013 — Tenancy and isolation
One shared schema in database `scf`; every tenant-owned table carries `tenant_id` (global tables have their own
policies — C-72); **RLS enabled and forced on every table and
every partition**; a RESTRICTIVE tenant policy as backstop; tenant context set per transaction with
`set_config('app.tenant_id', …, true)` and read as `(SELECT NULLIF(current_setting('app.tenant_id', true), '')::uuid)`.
Roles: `scf_migrator` (owner, DDL only), `scf_app` (control plane), `scf_writer` (inserts API metrics under a
tenant context — no bypass), `scf_jobs` (explicit cross-tenant policies for named jobs), `scf_metrics_ro`
(operator metrics API; may only execute the `op_*` functions). No runtime role has `BYPASSRLS`. Cross-tenant reads
by SCF operators go through allow-listed `SECURITY DEFINER` functions `op_*`, which apply the minimum-count threshold
and rounding and write the audit row in the same transaction; no application role can read across tenants any other
way (C-17). PgBouncer in transaction mode. Database gate tests: every table and partition has RLS + FORCE; no grants on
partitions; every tenant-facing view is `security_invoker`; every `SECURITY DEFINER` function is on the allow-list; plus
the HTTP isolation matrix (every endpoint × every role × own / foreign / missing / malformed IDs) and canary
tenants in production. We state that RLS protects against application bugs, not a compromised application.
*Re-run S-03 on real PostgreSQL 18.*

### ADR-0014 — Authentication, authorisation and roles
Sign-in: **GitHub OAuth** or **Stellar wallet signature** (SEP-53 message signing; SEP-10 challenge as fallback
for hardware wallets and multisig); **passkeys** (WebAuthn) as an added factor, **mandatory for operators**. No
passwords, no magic links, no e-mail sub-processor (an optional contact address may be stored). Built from small
libraries (`arctic`, `@simplewebauthn/server`, `@stellar/stellar-sdk`), not an embedded identity product.
Server-side sessions in PostgreSQL, `__Host-` cookie, `SameSite=Lax` plus an origin check and a custom header on
every state-changing request, idle and absolute timeouts (C-20).
Tenant roles: `owner`, `admin`, `member`, `viewer`. Platform roles: `operator` (global read, moderation) and
`operator_admin` (operators, API keys, enrollment mode). Operators are designated by an allow-list managed by
`operator_admin` and seeded at bootstrap. Every operator read of tenant data and every privileged action is
written to a hash-chained audit log.

### ADR-0015 — Enrollment and verification
Self-service by default (`enrollment_mode = open`); a single flag switches to `approval_required` with no
migration. Tenant states: `pending → active → suspended → removed`. Verification ladder shown to operators:
L0 unverified · L1 domain control (DNS TXT, `/.well-known/` file, or meta tag; re-checked periodically) ·
L2 Stellar-linked (SEP-53/SEP-10 signature by an account — C-19 — whose home domain and `stellar.toml` point
at each other) · L3 registry-matched (Stellarlight primary, PG Atlas secondary, nightly sync with provenance) ·
L4 operator-approved. L0 tenants are quota-limited and excluded from operator rankings by default. The domain
verifier is a separate egress-restricted worker (no private addresses, no redirects). Operator removal suspends
ingest within 60 s and purges data after a 30-day grace period; every step is audited.

### ADR-0016 — API keys and ingest tokens
Format `scfa_<kind>_<id>_<secret><crc32>`; 160-bit secret; stored as HMAC-SHA-256 with a server-side pepper; shown
once. Kinds: `op` (operator metrics keys: scopes `web:read`, `api:read`, `registry:read`, optional tenant
restriction, default expiry 90 days, revocable, rate-limited, last-used tracked, fully audited) and `ing` (tenant
OTLP ingest tokens: write-only, tenant-scoped with an optional service allow-list, up to five active — C-21) and
`pub` (tenant read-only share keys for the programme endpoint — C-14). Revocation reaches every edge node within 60 s
through the signed snapshot. The web **site key is public** and is not a secret. Umami's own API keys are internal
only (ADR-0003).

### ADR-0017 — Data residency
All visitor-derived and telemetry data is processed and stored only in the EU/EEA, on EU-based providers:
Hetzner (Germany/Finland), UpCloud (Finland; EU locations), OVHcloud (France), plus a small probe node at a fourth
EU provider. Backups in two EU providers. DNS at two EU providers. No CDN or third party sits in front of ingest.
A provider is called "EU-owned" only where that was verified. Exceptions, stated openly and none receiving
visitor-derived data: GitHub (source, releases, status-page history, scheduled probes of public endpoints);
Let's Encrypt (certificate requests); the npm registry (tracker package); optional on-chain correlation (public
ledger data only, off by default). Restore drills run only on EU infrastructure. Access by service-operator staff
from outside the EU is a transfer question for counsel. See C-26, C-56.

### ADR-0018 — Hosting and topology
Recommended tier (about €300/month, to be re-priced when ordering — C-25): four edge nodes `edge-a1`, `edge-a2`
(Hetzner, two locations) and `edge-b1`, `edge-b2` (UpCloud, two locations); `core-a` (Hetzner) and `core-b`
(UpCloud), each running PostgreSQL (Patroni), Umami behind the internal proxy, control plane, writer, jobs and the
portal behind Caddy; `mon-c` (OVHcloud) running monitoring, probes, the third etcd member, a health-controller
instance and the state/backup buckets; `probe-d` (fourth EU provider), probes only. Private traffic over a static
WireGuard mesh with per-node mutual TLS on internal hops. Providers are modules in the IaC and can be swapped
(Scaleway is the documented alternative if Hetzner capacity is unavailable). A lean tier (≈ €124/month in the
November 2026 research) is documented for the community operator.

### ADR-0019 — Infrastructure as code
**OpenTofu** (state in an OVHcloud object-storage bucket with native locking and state encryption) for
provisioning; **Ansible** for configuration; **Docker Compose** on Debian 13 for runtime; **SOPS + age** for
secrets. No Kubernetes, no Terraform, no Consul/Vault/Nomad. Images are referenced by digest and verified with
`cosign` in the deploy playbook. The same Compose files run the full stack locally, in tests and in production. *Depends on S-08.*

### ADR-0020 — High availability and spool
Web: an embedded append-only segment log on each edge node; the gateway answers `202` only after the record is
fsync'd (group commit); sealed segments older than 60 s that cannot be forwarded are also copied to the other
provider's object storage. Delivery to Umami is at-least-once; ambiguous retries are counted and reported.
OTLP: the Collector's persistent queue with fsync on; the writer de-duplicates. Traffic steering: multiple A/AAAA
records with TTL 60 pushed to two DNS providers; a health controller (two instances, etcd lease) removes dead
nodes; the tracker rotates between two ingest hosts; nodes drain by closing the listener. No message broker.
PostgreSQL: Patroni with synchronous replication (non-strict) across providers; dashboards fall back to read-only
from the replica.

### ADR-0021 — Backup and disaster recovery
pgBackRest (≥ 2.59.3) with two encrypted repositories at two EU providers, WAL archiving with a 60 s timeout,
point-in-time recovery; a weekly logical `pg_dump` as a tool-independent copy and the data-migration format for
handover; a weekly automated restore drill into a scratch instance with integrity checks and a published result.
WAL-G is the documented fallback if pgBackRest loses maintenance again. Targets (to be measured before they are
quoted): failover 30–60 s, rebuild from zero ≈ 4 h, data loss ≈ 0 with both database nodes healthy.

### ADR-0022 — Observability
Prometheus, Alertmanager, Grafana and VictoriaLogs on `mon-c`, outside the failure domain they watch; Gatus
probing every 30 s from three sources — `mon-c`, `probe-d` and cross-provider probes on the edge nodes — with a
2-of-3 quorum (C-30); a dead-man's switch run as a scheduled GitHub workflow; multi-window burn-rate alerts generated with Sloth; alerts to chat and e-mail (no on-call).
Public status page generated with Upptime in a separate repository (generated output, design trade-off DV-06); its
GitHub-hosted checks are an additional outside view at 5-minute resolution and are not used for the SLI. Logs never contain IPs, User-Agents, request headers or tokens.

### ADR-0023 — Release and supply-chain pipeline
Target design. Reproducible tracker build verified by an independent build; hash manifest signed with
Sigstore; npm **staged publishing**: the release workflow can only stage, a human approves with 2FA; two-person release via GitHub environment approval;
SLSA Build L3 provenance for the tracker and all images through an isolated reusable workflow; images signed with
cosign, SBOMs attached, referenced by digest. Dependencies: pnpm with `minimumReleaseAge`, strict build allow-list
and trust policy; Go with checksum DB, `govulncheck`; dependency updates with a 3-day delay and digest pinning; workflow
actions pinned by SHA with the Actions lockfile and least-privilege permissions. Scanners run as pinned,
signature-verified binaries in jobs without secrets, each with a known-vulnerable canary. CodeQL, licence
allow-list, secret scanning. 24-hour patch process triggered by CVSS ≥ 7, KEV listing or EPSS ≥ 0.1, with
compensating controls when upstream has no fix. Domain: registry lock, CAA, certificate-transparency monitoring.

### ADR-0024 — Portal stack
A static **Vite + React + TypeScript** single-page app talking only to the control-plane API; no server-side
rendering and no Next.js (smaller attack surface, simpler handover). TanStack Router and Query; uPlot for time
series; accessible tables for breakdowns. Strict CSP, no third-party scripts, and the portal dog-foods the
tracker. Views: tenant web dashboard, tenant API dashboard, operator web and API dashboards (aggregate, filter,
sort, side-by-side, verified vs raw, trust and assurance indicators), enrollment and verification, keys, audit,
erasure, onboarding wizard that generates SRI snippets and OpenTelemetry configuration per framework and language.

### ADR-0025 — Languages
Go for everything on the ingest path (gateway, Collector components, writer, path normaliser): one static binary
each, strong standard library for TLS and HTTP/2, the Collector's own language. TypeScript for tracker, portal,
control plane and jobs: one toolchain, shared types generated from the OpenAPI document. Plain SQL migrations
applied by a small migration tool run as `scf_migrator`. Tool versions pinned in `mise.toml`.

### ADR-0026 — Test strategy
Unit tests per package; integration tests against real PostgreSQL and the real Umami container; contract tests for
the Umami adapter; the path-normalisation vector corpus; end-to-end web path (Playwright browser → gateway →
Umami → portal) on static, SPA and SSR fixtures; end-to-end API path with Node, Python, Go and Rust SDK apps; the
cross-tenant isolation matrix and database RLS gates; bot and inflation simulations with asserted verdicts
(scripted POST, headless browser, multiplicity attack); load at 10× the design target; chaos (kill database,
engine, an edge node — ingest keeps answering 2xx and the spool drains); restore drill; rebuild from IaC into a
clean environment. Test runs write their evidence records (JSON and Markdown) to an evidence directory (`SCF_EVIDENCE_DIR`).

### ADR-0027 — Privacy and compliance posture
Roles: each tenant is controller for its site; the service operator is processor under a standard DPA (and controller for portal account data and audit logs — C-59); the SCF programme
receives **only anonymous per-tenant aggregates** (minimum count 10, rounded to 10, both configurable) and is
never given event-level data. No cross-tenant visitor de-duplication or reach is ever computed. No data that
identifies a person is stored (GDPR Art. 11 posture). Per-site settings: tracker profile, opt-out page, list of
countries in which no visitor identifier is derived (events counted as pageviews only). We state precisely where
consent-free operation is defensible (France, Spain, Italy, Netherlands under their published criteria; Switzerland
and the UK with notice and opt-out, the UK with caveats), where it is contested, and where it is not without opt-in — which, on the research, includes Germany, Belgium
and most other EU/EEA states for the `standard` profile, and China, Vietnam and Colombia (Russia because of
localisation). `docs/privacy/jurisdictions.md` is authoritative (C-41); a consent-gated tracker mode serves the
opt-in jurisdictions (C-55). The whole pack is marked "needs counsel
review"; legal fees are not a grant budget line.

### ADR-0028 — Trust score, API assurance levels and on-chain correlation
Web: a daily advisory trust score per site (0–100) with reason codes, from verified/raw ratio, proof statistics,
ASN mix, multiplicity flags and robust baselines of ratios that are hard to fake coherently; shown to operators
and, with explanations, to the tenant; tenants can annotate. API data is labelled **"self-attested telemetry"**
with assurance levels A0 (token only) · A1 (plausibility checks pass) · A2 (declared API base URL answers an
operator-side probe — liveness only) · A3 (on-chain consistency for declared contracts). On-chain correlation is
optional per tenant: daily counts per declared contract from SDF's public Hubble dataset, with our own reader of
the public ledger data lake as the rebuildable fallback. We state that on-chain activity can be bought cheaply and
is an indicator, not proof.

### ADR-0029 — Stellar Wallets Kit capture
Three tiers. **Tier 0 (on by default, zero configuration):** address-free DOM signals — the v1 kit's custom
events and the v2 kit's presence and modal open/close. **Tier 1 (one line):** `attachWalletsKit(kit)` or a
side-effect import, which subscribes to kit events and wraps sign methods, distinguishing a restored session from
a new connection. **Tier 2 (passive observation of wallet-extension messages): not shipped** — the listener would
be handed transaction data and addresses. Events: `wallet_modal_opened/closed`, `wallet_selected`,
`wallet_connected`, `wallet_session_restored`, `wallet_disconnected`, `sign_requested/completed/failed {kind}`. An
allow-list serialiser sends only event type, wallet id (closed set, `freighter`/`varial` aliased) and sign kind —
**never addresses, XDR, signatures, memos or error text** — enforced by a test on the outgoing request.

### ADR-0030 — Right-to-erasure workflow
Because no identifying data is stored, erasure concerns personal data that leaks into paths, titles (not collected
by default), custom-event names and properties. A tenant `owner`/`admin` can request deletion by site, time range,
path pattern, event name or property key; the request shows a count preview, runs as an audited job against the
`umami` database and our aggregates, and reports completion. Backups expire on their retention schedule (stated).
Removing a whole site or tenant uses the same machinery. End users are directed to the tenant (controller); the
platform provides the tenant with the notice text.

### ADR-0031 — Service-level indicators and objectives
Ingest availability SLI = accepted ÷ valid requests at the edge, where accepted means a 2xx **after durable
persistence** within 2 s; measured from server logs and independently by 30-second external probes with quorum;
target 99.99 % per calendar month, no maintenance exclusion. Dashboard availability SLI = successful synthetic
journeys ÷ attempts; target 99.9 %. Also published: durability (no accepted event is lost unless it could not be
delivered for more than 72 hours — C-18) and freshness (99 % of accepted events visible within 5 minutes, 99.9 %
within 60 minutes — C-28, C-43). The headline availability figure is the probe-based one. Error-budget policy, monthly public report with raw probe data, public
post-mortems. Support: first response ≤ 5 business days, resolution ≤ 10, tracked by issue automation.
Critical/high vulnerabilities patched or mitigated within 24 h.

### ADR-0032 — SCF programme integration
For projects in the SCF programmes: a per-tenant **`metrics_endpoint` JSON** and platform **`health_endpoint`** compatible
with what the SCF Public Goods programme already polls; **signed traction snapshots** a tenant can attach to a
Growth Hack, Public Goods or Integration Track application and anyone can verify against the platform; operator
exports for campaign-versus-baseline comparison. These serve trust.verified-vs-raw, operator.real-usage-ranking and share.signed-usage-report.
