# Measured engine ceiling — web and API paths (2026-11-19)

**What this is.** The capacity runs before this one (`tests/load/run.ts`, `run-api.ts`) hold one rate (10× the design
target) and prove nothing is lost. This run ramps the load until something saturates and records where, so the
design target (approximately 1 000 000 API requests per day across all tenants, capacity.1m-requests-day; and 1 M page views/day,
C-48) can be compared with a measured ceiling instead of an assumption.

**Status of the numbers.** Measured on one development host, from a working tree with uncommitted changes in
unrelated services (jobs, on-chain reader) — the raw evidence files therefore carry `-dirty`. The gateway, engine
proxy, Umami, Collector and writer images were those of commit `pre-release`. These are **not** production figures: the v1
production VM (2 vCPU / 8 GB) must be measured with the same command (below) once deployed.

The raw per-run reports (Markdown plus machine-readable JSON) are written by the load command below and are not
kept in the repository.

## Machine

| | |
|---|---|
| Host | KVM/QEMU virtual machine, Intel Core Ultra 5 225, **8 vCPU**, 51 GiB RAM, SSD-backed virtual disks, Linux 6.12, Docker 29.7 |
| Stack | `infra/compose` single node (one gateway, one engine proxy, one Umami 3.5.0, one PostgreSQL 18 behind PgBouncer, one Collector, one writer), project `rvt` via `tests/load/stack/up.sh`; counters/snapshots every 5 s, otherwise shipped settings |
| Load client | Node 24 on the **same host** (shares the CPUs); TLS to the gateway like any internet client |
| Other load | the host also ran image builds during parts of the run; figures are a floor, not a best case |

## Method

`tests/load/ceiling.ts` (ceiling mode of the load suite), bounded to ≤ 18 minutes per part:

- **Web:** open-model page views (one event per request; challenge + proof of work once per 250 page views, SPA token
  reuse) over 8 sites, stepped rates of 45–60 s each. Per step: answers, latency, the spool's intake (`fsynced`/s), the
  forwarder's delivery into Umami (`acked_stored`/s) and the spool's growth. **Saturation = the spool grows during a
  step** (delivery below intake); the ramp stops there. Then the load stops and the **drain rate** (delivery with no
  ingest competing) is measured. Finally Umami must hold exactly the accepted events.
- **API:** OTLP/HTTP JSON, 100 SERVER spans per request, 12 tenants × 50 routes, stepped 1 000 → 10 000 spans/s. Per
  step: answers (200/429/503), latency, the writer's row writes/s (inserts + updates on the `api_*` tables,
  `pg_stat_user_tables`). Saturation = < 99 % answered 200 or p99 > 2 s. Then: time until the control-plane API reports
  every accepted span as a request.
- Tenant protections (per-site/subnet rate limits, L0 quotas, OTLP per-tenant limits) are raised for the run and restored
  after; the adaptive proof-cost multiplier is set to 1 so the client's own proof solving is not what saturates. These
  are protections, not capacity limits.

## Results — web (gateway → spool → forwarder → engine proxy → Umami → PostgreSQL)

Shipped configuration (16 forwarder workers):

| Offered ev/s | Answered 202 | p50 / p99 ms (fsync before 202) | Spool intake /s | Delivered to Umami /s | Spool growth /s |
|---:|---:|---:|---:|---:|---:|
| 80 | 100 % | 23 / 81 | 79.6 | 79.6 | 0 |
| 100 | 100 % | 30 / 130 | 99.4 | 98.6 | 0.7 |
| 115 | 100 % | 27 / 101 | 114.4 | 114.0 | 0.4 |
| 130 | 100 % | 22 / 82 | 129.0 | 129.3 | −0.3 |
| 145 | 100 % | 22 / 83 | 144.3 | 144.3 | 0 |
| **160** | 100 % | 24 / 90 | 159.6 | **159.7** | 0 |
| 200 | 100 % | 24 / 98 | 198.7 | **165.3** | **33.5 (saturated)** |

Drain after the ramp: 2 065 queued → 0 in 11.2 s = **184.5 events/s**. Umami holds exactly the 55 800 accepted events
(no loss, no duplicate).

Sensitivity run with 64 forwarder workers (4× the default): saturated at the same point — delivery 162 events/s at
200 offered, drain 163 events/s, 15 750 accepted = 15 750 stored. More forwarder concurrency does **not** raise the
ceiling, so the limit is the engine (one Umami process; CPU samples 60–70 % of one core with PostgreSQL at 10–15 %,
i.e. the per-request work in Umami and its database round trips), not the gateway or the forwarder. An exploratory
first ramp on a cold stack (no evidence file, log only) saturated earlier: 126 events/s delivered, drain 128 events/s.

**Web engine ceiling on this host: ≈ 160 events/s sustained (≈ 125 on a cold stack; 165–185 peak/drain).** The
gateway's own intake was never the limit: it accepted 200 events/s with fsync'd 202s at p99 < 200 ms and buffers the
difference in the spool, which drains at the engine rate afterwards.

## Results — API (OTLP front door → Collector → writer → PostgreSQL)

| Offered spans/s | OTLP req/s | Answered 200 | p50 / p99 ms | Writer row writes/s |
|---:|---:|---:|---:|---:|
| 1 000 | 10 | 100 % | 13 / 47 | 50 |
| 2 500 | 25 | 100 % | 14 / 83 | 12 |
| **5 000** | 50 | **99.7 %** (7 × 503) | 14 / 258 | 13 |
| 10 000 | 100 | 91.2 % (395 × 503, 3 × 429) | 37 / 508 | 10 |

Saturation at 10 000 spans/s offered: the front door answers `503` + `Retry-After` (Collector queue / in-flight bound;
SDKs retry, nothing is silently lost). All **792 000 accepted spans** appeared as requests in the control-plane API,
caught up **313 s** after the ramp (the Collector aggregates spans into metrics and the writer drains its queue). Peak
writer rate observed: **182 row writes/s** over a 10-s window; the writer was not the bottleneck (the Collector
aggregates, so writer rows scale with route/status cardinality, not with request volume). The writer's own
ceiling test remains `services/metrics-writer/integration/zz_load_test.go` (1 500 metric points/s sustained).

**API path ceiling on this host: ≈ 5 000 spans/s (= tenant API requests/s) through one gateway + Collector.**

## How this scales to the design target of 1 000 000 requests/day

| | Design target | Average rate | Assumed peak (5× average) | Measured ceiling (this host) | Headroom at peak |
|---|---|---:|---:|---:|---:|
| Web page views | 1 M/day (C-48) | 11.6 /s | 58 /s | ≈ 160 /s sustained (125 cold) | ≈ 2.2–2.8× (≈ 11–14× at a flat average) |
| API requests | 1 M/day (capacity.1m-requests-day) | 11.6 /s | 58 /s | ≈ 5 000 /s | ≈ 86× |

- One Umami instance on this host handles ≈ 13.8 M events/day if traffic were flat (≈ 10.8 M on a cold stack); with a
  5× peak-to-average day it handles ≈ 2.8 M/day without the spool growing at the peak. Bursts above the engine rate
  are absorbed by the fsync'd spool (accepted with 202, delivered later; 72 h bound) — e.g. a one-hour peak at 300
  events/s leaves ≈ 0.5 M events that drain in ≈ 1 h at 160/s.
- The API path is ≈ 430 M requests/day flat on one node — the design target is not close.
- Beyond one engine: Umami is stateless in front of PostgreSQL, so more Umami processes behind the engine proxy (the
  documented scale-out profile) raise the web ceiling until PostgreSQL is the limit; that is not measured here.
- **The production VM has 2 vCPU** (vs 8 here, shared with the client). Umami is single-threaded, so the per-core
  speed matters more than the core count, but the gateway, PostgreSQL and the client share fewer cores; expect a lower
  figure and measure it.

## Reproduce

```sh
eval "$(mise env -s bash)"
tests/load/stack/up.sh                         # project rvt, ports 56540–56549 (images built beforehand)
eval "$(tests/load/stack/env.sh)"
cd tests
node load/ceiling.ts --part web --steps 80,100,115,130,145,160,200 --step-s 60
RVT_FORWARD_WORKERS=64 ../tests/load/stack/up.sh && node load/ceiling.ts --part web --steps 150,200,250,300 --step-s 45   # sensitivity
node load/ceiling.ts --part api --step-s 45    # default 1000,2500,5000,10000,20000 spans/s, stops at saturation
../tests/load/stack/down.sh
```
